# Decisions

Taken in phase 0 on 2026-10-22, from `spec/14-open-questions.md` and the user's instructions for the build. Each item says where the package was changed to match. Later phases add their readings of unclear spec points at the end.

## From spec 14

1. **Name.** The product, CLI and plugin are called `factory`. The CLI name is one constant in the code.
2. **Install.** The primary install is a Claude Code plugin, so the factory can be shared with other people (item 12). Copies (`factory skill install --user|--repo`) and `factory skill plugin <dir>` stay as alternatives.
3. **Adapters in v1.** `github` and `github-issues` are the adapters in daily use: their scripts are built and tested in phase 2. `none`, `git` and `local` are part of the core. `figma` ships as written: it is MCP only, so there is nothing to build. `gitlab`, `bitbucket`, `jira` and `linear` ship as folders with `adapter.json` and `adapter.md`; their scripts are not built, and a script capability whose file is missing reports `not built`, a visible skip. More adapters later are welcome but low priority. Custom MCP adapters must be easy to add (item 13). Applied to 07.
4. **Tracker write-back.** Off by default. With `"write": true` on the tracker and `comment` available, Finish posts one comment with the PR links, and never changes the external issue's status or fields. The spec already says this (07, 09).
5. **Files jobs.** They stay in `out/`. A docs change in a repo is a `code` job with `write-doc` as its producer. The spec already allows this (06).
6. **Code review.** `defaults.require_code_review` is true by default; a project can turn it off. The spec already says this (06, 08).
7. **Human gates.** Option A of a human gate's `## Ask` approves. An answer of `A`, alone or with a note (`A: <note>`), is PASS, and the note goes under the gate file's Notes. Any other answer is CHANGES, with the answer as the Must fix item. Applied to 06 and the skill.
8. **Reference data.** Not imported. The factory starts clean. Changed on 2026-10-23 at the user's request: `factory legacy import` brings the reference's merged jobs, retro proposals and answers in as finished runs, improvements and answered questions (README, "History from the old factory").
9. **Shared use.** One factory home per user and machine. The local tracker is a personal and factory backlog, not a team tool. Sharing the plugin with other people is a separate matter: each of them gets their own home.
10. **Price table.** The built-in table carries the date its prices were checked. `usage show` and the dashboard show that date next to costs, and `prices.json` overrides the table with its own date. Applied to 10 and 11.

## Readings of unclear points

- The build folder was not a git repo. It was initialised with `git init` (branch `main`) at the end of phase 0, with no commit.
- `examples/` from this package ships at the top of the core's repo, beside `catalogue/` (02, Source layout).

### Phase 1

- **Run ids** are `<YYYYMMDD>-<HHMMSS>-<slug>` in UTC, with the slug from the feature or issue title (at most 24 characters) and `-2` and so on on a clash.
- **Job branches** are `<feature_branch>--<job-id>`. A branch cannot sit under the feature branch's name (`feature/x/job`), because git keeps branches as paths.
- **`group.agent`** in `job start`, `job next`, `job show` and `job rework` is the step's agent (`factory-worker`, a dedicated agent or `human`), as the skill maps it to a `subagent_type`. The name or id stored with `job agent` is `group.producer`. Phase 3 aligns the skill's "its stored agent in `job show`".
- **Prompt-ready values.** `sources`, `upstream` and `previous` come back as comma lists or `none`, ready for a prompt line. Every other value that does not apply is JSON `null`.
- **`catalogue check`** prints its JSON report and exits 1 when it finds problems. `catalogue show` and the run snapshot leave out files that do not parse or validate, keep the earlier entry of the same name, and list the files under `problems`.
- **Storing a question again** returns the existing question only while it is not resolved. So the same human gate question in a later round, or after a rework, is a new question.
- **Human gates.** The note of a PASS goes under Notes as `[human] <note>`, so it reaches the PR's Open points. `gate sync` is `complete` when every agent gate has a verdict and either one asked for changes (the human gates are then not asked) or every human gate has answered too. `gate human` refuses while an agent gate of the round has not passed.
- **WAIT FOR ALL in code.** `job round` refuses while the round's gates are still out, so a producer cannot be resumed on a mixed round.
- **Skips at `run new`**: the ad-hoc project, knowledge and step-skill paths that do not exist, a code host that cannot push (`none`), each repo without an `origin`, and a missing `open_pr`. `mcp` and `skill` capabilities are left to the session check, as the skill says. When `run new` gets no `--repo`, `plan load` adds the repos, records their skips and sets `no_pr` when none of them can push.
- **`--base`** is kept in the `run.new` event, so it also applies to the repos `plan load` adds.
- **A run never starts in a repo outside its project.** `--repo` takes a repo name of the project or the path of a linked checkout, and anything else is refused. When the current folder resolves no project and `--repo` is a path, the project is resolved from that path. `--issue` without `--project` uses the issue's project.
- **Default branch** of a repo: the configured one, else `origin/HEAD`, else `origin/main` or `origin/master`, else the local `init.defaultBranch`, `main` or `master`, else the checkout's current branch.
- **Paths in config files.** Paths the CLI writes are stored expanded. A `~` written by hand stays in the file and is expanded on every read.
- **`run archive` and `run delete`** refuse a run that is not done or failed unless `--force`. `--force` never overrides the refusal for accepted improvements that are not applied. `delete` also removes the local feature branches; remote branches are never touched.
- **`run status`** to the run's current status changes nothing and reports `changed: false`.
- **Migrations.** `factory/schema.sql` is version 1, and later versions are files appended to `db.MIGRATIONS`. With one version the migration test covers an empty database (version 0) to version 1; it runs over every older version as versions are added.
- **Modules.** Besides the modules the brief lists: `home.py` (the factory home and `config.json`), `doctor.py`, `plans.py` (reads and validates `plan.md`, writes nothing), `heads.py` (file heads and sections) and `util.py`.
- **Adapter availability** was built in phase 1, because `project show` and `run new` need it. The script protocol, `adapter run`, `adapter new` and the adapter scripts stay in phase 2. A `git` push where only some repos have an `origin` is `partial`, with the state per repo.
- **`issue.md` for a local issue** has `Assignee: none`, `Parent: none`, no comments and no attachments; Linked issues come from the issue's links.
- **Not checked by code:** the plan's "no factory words" rule for job titles. `plan load` checks that a title is one line of at most 200 characters.
- **`config set`** logs a `config.set` event with the key, never the value.

### Phase 2

- **The script protocol.** The core keeps only the last line of a failing script's stderr (at most 300 characters), with every value of the capability's `requires.env` names replaced by `***`. A script's output is checked per capability (`pr_state`: a known state and a url; `open_pr`: `created` or `updated` and a url; `sync`: a list of issues with `external_key`; `fetch_issue`: a title), and anything else is "unknown, change nothing". A placeholder has no value when its setting is null and the project sets none; the repo placeholders are empty strings for project-level calls.
- **`adapter run`** takes `--<placeholder> <value>` with `_` or `-` in the name, and `--name=value`. `--project` and `--repo` are its own flags, and unknown placeholders are ignored. The adapter must be one of the project's adapters, and the capability a script that is `available`. Exit 3 passes through with a message on stderr instead of JSON.
- **PR states come from the current project config**, not the run's snapshot, as Publish already does, so a code host added after the run counts. `run pr` checks the url against that code host's `pr_url` pattern (any http or https url when it has none) and clears the stored state. The issue moves to `in_review` only from `open`, `ready` or `in_progress`.
- **`run prs`** without a run id checks every run that is not archived and has PRs. A failing script reports `unknown`; a host without a script `pr_state`, a script not built, a missing tool or missing credentials report `unchecked`; neither changes the stored state. The issue moves to `done` when every repo of its latest run that has a PR is `MERGED`; repos without a PR do not count.
- **`issue sync`** changes title, url, external status and `synced_at`, never the local status, lists the mirrors the script did not return, and exits 3 when credentials are missing.
- **Designs.** `design links` uses the run's snapshot when the file is in a run folder, else project resolution or `--project`. Without a design adapter it returns no links and the reason. `design target` keeps `design/.targets.json` (frame name to file name), so asking again for the same frame returns the same paths; the names `notes` and `readme` are kept free. Hidden files do not count as designs for `requires: [designs]`. `design check` deletes every `.png` in `design/` without the PNG signature and removes scrub matches from every `.md` file there.
- **`retro load`.** A second load updates the run's items by key and keeps their decisions, and removes the `open` items that are no longer in the file. An item with `same_as` needs only `key` and `same_as`, which must name an improvement of an earlier run. `seen_in` starts with the run's own id.
- **Improvement moves:** `open` to `accepted` or `rejected`; `accepted` to `done`, `rejected` or `open`; `rejected` and `done` back to `open`. Back to `open` clears the PR and the branch and reopens the linked issue. The issue of a `factory` item goes to the `factory_project` project when that project exists.
- **Improve groups.** A `factory` group uses the `factory_project` project, with its repo's `setup`, when that project links the factory source; otherwise its project file is a minimal project with the factory source as its only repo, the local tracker and no code host. Groups are keyed by repo path and base branch; a second group in the same repo gets `-2` on its branch and folder. A group's project file comes from its first item. Each group also returns `setup`. The batch id is a UTC timestamp. `improvement prs --check` reads states through the code host of the item's project (`factory_project` for `factory` items).
- **Token usage.** `CLAUDE_CONFIG_DIR` replaces `~/.claude` when set, as Claude Code does. Within one sync, the line of a message id with the most output tokens counts; ids seen in an earlier sync (the last 64) are skipped; a last line without a newline waits for the next sync; `<synthetic>` messages are skipped. Subagents without a factory prompt count as node `other` in the orchestrator's run, and improver transcripts (`run_dir: none`) are not counted. A producer's rounds come from the `job.round` events of its group, found from `group_dir`.
- **Price table**, dated 2026-10-22, from the Claude API reference (cached 2026-10-06), in dollars per million tokens (input / output / cache read): Fable 5.1 and Mythos 5.1 10 / 50 / 0.25; Fable 5 and Mythos 5 10 / 50 / 1; Opus 5.5 4 / 20 / 0.2; Opus 5, 4.8, 4.7 and 4.6 5 / 25 / 0.5; Sonnet 5.5 and 5 2 / 10 / 0.2; Sonnet 4.6 3 / 15 / 0.3; Haiku 5.5 0.1 / 0.5 / 0.01; Haiku 4.5 1 / 5 / 0.1. Model ids match by prefix (a date or `[1m]` suffix still matches). Haiku 5.5's higher price above 100K-token prompts, and batch and fast-mode prices, are not modelled. `prices.json` is `{"date": "YYYY-MM-DD", "models": {<id>: {"input", "output", "cache_read"}}}` and replaces the whole table.
- **The v1 scripts** (`github/scripts/pr_state.py`, `github-issues/scripts/sync.py`) follow their adapters' "Scripts to build". `pr_state.py` reads the `pr_url` pattern from its own `adapter.json`, so a project's pattern override for a self-hosted instance passes the core's check but not the script's; such a host needs its own script. The scripts' tests are in each adapter's `tests/` folder.
- **`adapter new`** marks what to fill in as `<fill in: ...>`, and `catalogue check` counts these in `adapter.json` and `adapter.md`.
- **Changes to the shipped package:** none to the prompts. The catalogue gained the two scripts and their tests, as the adapters' "Scripts to build" sections ask.

### Phase 3

- **The plugin** is this repo: `.claude-plugin/plugin.json` (name `factory`, the core version, a description, author `factory`) and `.claude-plugin/marketplace.json` (marketplace `factory`, owner `factory`, one plugin with `"source": "./"`; the version is only in `plugin.json`, as the marketplace reference advises). Users install it with `/plugin install factory@factory`. Both files pass `claude plugin validate` (Claude Code 2.1.308). No `LICENSE` is set: the plugin installs without one, but Anthropic's plugin directory requires one before a listing, and that choice is the owner's.
- **Self-copy.** Every command checks whether the CLI runs from a plugin folder (one with `.claude-plugin/plugin.json`) that is not itself under `$FACTORY_HOME/core/`. If so, it copies the core parts (the same list as `install.sh`, without `__pycache__`) to `core/<version>/` when that folder is missing, and points `core/current` at the version with an atomic rename, and logs a `core.sync` event. A git checkout of the core is such a folder too, so running a checkout copies it the same way.
- **Installs** keep a manifest, `.factory-install.json`, in the installed skill folder (in the folder itself for `skill plugin`), listing each installed file and its source. `uninstall` removes only those files, and a new `install` removes files a previous one wrote that are no longer part of it. The `installs` row's `path` is the `.claude` folder (`~/.claude`, `<repo>/.claude`) or the plugin folder. An install is current when its version is the core's and every file still matches its source.
- **Dedicated agents** are installed when a step names them and their file is in a catalogue `agents/` folder: built-in, the factory home and `config.json` `catalogue_dirs` for `--user`; plus the project's folders for `--repo`. A repo install resolves its project from the repo when `--project` is not given; it may have none.
- **`factory agents`** looks for each agent in `<repo>/.claude/agents/` (the git toplevel of the cwd), then `~/.claude/agents/`, then the plugin's `agents/`: the core's own when the CLI runs from a plugin folder, and folders written by `skill plugin`. A plugin agent's `subagent_type` is `<plugin name>:<agent>`. `scope` is where the planner was found, `null` when nowhere. Each role's value is `null` when its agent is missing, and the agent is listed under `missing`.
- **`skill plugin <dir>`** writes the skill, the agents and a `plugin.json` named `factory`, and refuses a folder that holds other files. It has no `bin/`: the skill's `F=` line then falls back to the `factory` command on PATH or `core/current`.
- **`project show`** adds `installs` (the user install, the repo installs of the project, and the plugin folder) to its output. The run snapshot and the dashboard do not carry it.
- **`doctor`** checks the skill: the plugin, or a current user install; and every other install that is not current, with the command that refreshes it.
- **Prompt changes (phase 3).** The skill now says that `job show` returns the stored producer as `group.producer`, and that `group.agent` is the step's agent (Agents, and Questions). Both `factory-spec/prompts/skill/factory/SKILL.md` and `skills/factory/SKILL.md` changed; a test keeps them equal. Every other CLI call, flag and JSON field named in the skill, the agents and the adapters matched the code.
- **The shell test** also runs `bash -n`, besides `sh -n` and `zsh -n`. zsh is not installed on the build machine, so that part skips.

### Phase 4

- **The server** is `http.server`'s threading server on 127.0.0.1, one database connection per request. `factory serve` uses `--port`, else `config.json` `dashboard.port`. A refused `Host` is 403, a cross-origin POST 403, a POST that is not `application/json` 415, a body that is not a JSON object 400, a body over 1 MB or a text over its limit 413, an unknown route 404, other methods 405. Errors are `{"error": "<message>"}`; a core error whose message starts with "no " is 404, other core errors are 400. Responses carry `Cache-Control: no-store`, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` and a Content Security Policy that allows only the page's own inline script and style, images from the server or `data:`, and requests to the server itself.
- **Routes added to spec 10's list:** `GET /api/meta` (the version, the factory home and the price table's date, for the sidebar). `GET /api/runs?archived=all` returns active and archived runs together. `GET /api/runs/<id>` also returns the run's files (`.md`, `.json`, `.png`, at most 500) and, for the steps its jobs use, the catalogue entry with the step's Focus items, for the loop graph's step view. `GET /api/projects/<name>` also returns the merged catalogue and the skill installs; `installs.plugin` is `true` or `false`, because the plugin's path is outside the repos and the factory home. `GET /api/questions` marks the plan confirm (`kind: "plan_confirm"`: a question of the orchestrator whose path is the run's `plan.md`) and adds the run, the job and, for a plan confirm, the jobs with their pipelines.
- **Writes from the dashboard** go through the core functions with author `dashboard`; answers and follow-ups are not marked delivered, so the orchestrator's `question wait` returns them. `POST /api/issues/<KEY>` takes `labels` as the full list and works out which to add and remove; `body` replaces the body text. Archiving from the dashboard needs a done or failed run (no `--force`).
- **Redaction** for `GET /api/projects/<name>`: every absolute path outside the factory home and the project's repos becomes `null` (or leaves a list), and every adapter setting with `"secret": true` reads `***`. Adapter settings may now carry `secret`.
- **File reads** take an absolute path or one relative to the factory home. Paths are resolved (`realpath`) before the folder check, so `..` and symlinks that leave the folder are refused.
- **Usage** is synced each time a run is opened or polled, and errors there never fail the request. The PR poller runs `run prs` every 5 minutes in a daemon thread, which skips final states and reloads project config on each pass; a failed pass is printed on stderr and the next pass runs as usual.
- **The page** builds every element with `textContent`; the markdown renderer creates elements, not HTML strings, and supports headings, paragraphs, lists with checkboxes, tables, code, quotes, bold, italics, inline code, `http(s)` and `#` links (opened with `rel="noopener noreferrer"`), and `<details>` with `<summary>`, which it rebuilds. View state that is not in the URL (the run view, the theme, the project picker, the run filter) is kept in `localStorage`. The hatched gaps of the timeline are drawn with an inline SVG, because the CSS gradient keyword contains a vendor word of the neutrality list.
- **`factory demo`** seeds a project `demo` with two local repos (no `origin`), five issues and three runs: one running with a waiting producer question, one waiting for its plan confirm, and one done with a retrospective and three improvements. It goes through the same functions as the CLI and refuses when the project exists.

### Phase 5

Taken during the acceptance walk-through on 2026-10-22, from what the live runs showed. The user decided items 1 to 5.

1. **Refused writes.** In auto mode, Claude Code tells subagents to hand their final report back, and its Write tool refused a research worker's `out/findings.md` ("Subagents should return findings as text, not write report files"). The refusal comes from the tool, so allow rules don't help. A gate also ended without its review file, believing it had no write tool. Fix: agents return refused files as `=== FILE: <path> ===` blocks, and the orchestrator stores them unchanged with the new `factory step save`, which accepts only the agent's own files (05, Refused writes). The worker and reviewer prompts and the skill say so.
2. **Dropping a job.** The CLI had no way to give a job up, so a run reached `done` with a job left `running`. Fix: `factory job drop <ref> "<reason>"` and the stage `dropped` (schema version 2, which rebuilds `jobs` with foreign keys off). `job ready` reports jobs blocked by a dropped dependency. `run status finishing|done` refuses while a job is neither done nor dropped, and a dropped job can be reworked.
3. **The plan confirm is asked in chat as plain text,** no longer with AskUserQuestion. A question box blocks the session, and a dashboard answer could not close it, so the user had to answer twice.
4. **Moving rarely used parts of `SKILL.md` into files read on demand** is left for after phase 5. The orchestrator was 57 to 70% of each run's cost.
5. **License: MIT,** copyright yoieh, chosen by the owner after phase 5. `LICENSE` is at the repo root and `plugin.json` says `"license": "MIT"`.

Fixed without a decision, as phase 5's "fix what breaks":

- A Worktree setup line such as ``none needed; `python3` on PATH is enough`` became the setup command `python3`. A line that starts with none, n/a, nothing or not needed now means no setup, and the planner is told to write exactly `none`.
- The retrospective's commit check (and the improver's description of its worktree) assumed an `origin` remote; they now fall back to the local base branch.
- A core copy under `$FACTORY_HOME/core/` counted as the plugin, because `install.sh` copies `.claude-plugin/`. It now counts only when the plugin's self-copy made it, and then it points back to the plugin folder (`.plugin-source`).
- The dashboard folds a question that is already answered, and shows `dropped` jobs.
- The Confirm box stayed on wait until the session read the dashboard's answer and moved the run, about ten seconds later. It now turns done as soon as the plan confirm is answered yes (yes, y, approve, approved, ok, okay); any other answer shows the Planner running again. The run's status pill still shows the run's real status. The run detail marks each question's `kind`, as the question list already did.

### After phase 5

- **The dashboard over Tailscale** (2026-10-23, asked by the user). The server still binds 127.0.0.1; `tailscale serve` proxies the tailnet name to it and keeps the browser's `Host`. `config.json` `dashboard.hosts` lists extra host names (lowercase, no scheme or port) that the Host and Origin checks accept on any port, because the proxy's port need not match the local one. `factory serve` reads it at start. No bind option was added, so nothing listens outside loopback.
