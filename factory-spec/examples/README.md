# Examples

Example configs for the factory. All names are fake: the project `shop` with key `SHOP`, the GitHub owner and Bitbucket workspace `example`, the Jira site `example.atlassian.net`. A project config lives at `$FACTORY_HOME/projects/<name>/project.json`, the global config at `$FACTORY_HOME/config.json`. The CLI writes both and validates them on every read, so an unknown key, or a setting an adapter does not list, is an error. Credentials never go in either file.

`project.minimal.json` is the smallest valid project: a name, a key and one repo. It names no integrations, so the tracker is the local issue list and the code host is `none`: runs build, review and merge into a local feature branch, run the full tests and stop without a push. It has no knowledge paths, step skills or defaults, so the agents read only the repo and the built-in catalogue.

`project.github.json` links two repos, an API and a web app, on GitHub. Issues come from GitHub Issues through `gh` (`/factory 12` or an issue link), and the `repository` setting names the repository that holds them; issue numbers are the keys. The `github` code host pushes each feature branch and opens one draft PR per repo with `gh`, and asks the `reviewers` team for review on top of the repo's code owners. `write` is false, so nothing is written back to the issues. The knowledge paths point at docs inside the repos: the planner and every agent read `read_first`, the `per_repo` file of each repo they work in, and the `architecture` file for architecture reviews.

`project.full.json` uses every key a project can have. It links three repos on Bitbucket (an API, a web app and a docs repo), reads issues from Jira through the Atlassian MCP server (its `patterns` override narrows the Jira keys to the `WEB` and `PAY` projects, so they never clash with the local `SHOP` keys, and `status_map` suggests a local status for each Jira status on the dashboard), opens draft PRs through the Bitbucket REST scripts with the repos' default reviewers, and fetches Figma frames into each run's `design/` folder. `repo_root` lets the planner propose repos that are not linked yet. `step_skills` attaches the team's own standards to steps by their `skills_key`. `catalogue_dirs` adds the team's own step files and pipeline templates. `improvement_targets` keeps the four standard targets and adds a custom one, `runbooks`, that lands in the docs repo on `main`. `defaults` sets the run defaults; here every run confirms its plan.

`config.json` is the global config of one machine. `default_project` is the project used when nothing else resolves one. `dashboard.port` is the port of `factory serve`. `factory_source` is a git checkout of the factory itself, where improvements with target `factory` are applied; `factory_project` is the project whose issue list holds those improvements (create it first, for example `factory project add factory --key FAC`). `catalogue_dirs` adds catalogue folders for every project on the machine. `parallel` and `max_rounds` are the run defaults when a project sets none.
